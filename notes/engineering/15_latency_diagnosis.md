# 15｜检索延迟排障：先定位时间花在哪，再提出优化

> 复习主线：先区分排队变慢还是执行变慢，再提出可能原因，用监控和对照实验验证，必要时先恢复服务。

## 面试题目（提供给候选人）

一次索引更新后，检索服务 P99 从 40 ms 升到 150 ms，QPS 大致不变。P99 表示 99% 的请求耗时不超过的值，QPS 表示每秒查询数。请说明排查顺序、需要补充的指标、可能原因与验证方式；写一个有界队列和阶段耗时的最小示例。

- 建议 30 分钟；考察如何根据测量结果排查问题，不要求背工具命令。
- 只知道延迟升高发生在更新之后，不能直接假定“就是 merge”或“就是锁”。
- 示例区分入口到出队、执行、总耗时，并显式记录队列满拒绝。
- 用 steady_clock；教学示例不作为吞吐、P99 或性能基准。

## 面试官答案：先问哪一段变慢

```text
到达 t0 → 入队/排队 → 出队 t1 → 执行检索 → 完成 t2
queue = t1-t0        execute = t2-t1       total = t2-t0
```

本例 t0 在 try_push 前，queue 包含很小的入队锁开销，实际测量的是从请求到达到工作线程开始执行的时间。若要单独测量进入队列之后的等待时间，应该在任务实际加入队列时再记录一个时间戳。先明确测量的起止位置，才能正确解释数据。

📌 代码依据：[耗时记录示例](../../engineering/retrieval/15_latency_diagnosis.cpp)：

```cpp
const auto end = Clock::now();
timings.push_back({request.id,
                   micros(begin - request.arrival),
                   micros(end - begin),
                   micros(end - request.arrival)});
```

有界队列仅限制积压，不自动提高服务能力。示例先让工作线程等待启动信号，填满两个位置，第三次明确拒绝，再允许工作线程运行，处理完队列中的任务。这是用确定的同步制造过载场景，不靠 sleep 或耗时大小断言成功。

## 排查框架：每个假设都要配证据

| 现象/假设 | 先查证据 | 有证据之后的处理 |
|---|---|---|
| 排队变长，执行稳定 | 队列内任务数、排队时间分布、到达/完成/拒绝速率、线程数 | 检查允许的并发数和请求是否突然集中到达，必要时限制流量或减少非必要处理，不盲目扩大队列 |
| 执行变长，CPU 高 | CPU 各函数耗时分析、倒排列表长度、解码量、候选数、查询词分布 | 定位扫描/评分热点，验证剪枝、缓存或数据变化 |
| CPU 不高但等待多 | 等待互斥锁的时间、阻塞线程的调用栈、线程状态、未在 CPU 上运行的时间（off-CPU time） | 检查是否长时间持有互斥锁或等待其他服务，减少持锁期间的工作，或给不同任务分配独立资源 |
| 更新后所需数据不在缓存中 | 索引版本、缓存命中率、缺页次数（访问内存页时需要系统额外处理）、提前加载常用数据后性能是否恢复 | 提前加载常用数据或分批启用新版本，区分缓存未准备好与程序计算真的变慢 |
| 索引段合并或 I/O 干扰 | 合并开始和结束时间、磁盘延迟/队列、读取量、内存带宽 | 限制后台资源，调整合并时机和同时执行的合并任务数 |
| 只有部分实例/分片慢 | 分片命中量、段数、删除率、CPU、访问特别频繁的 key | 确认数据倾斜、慢节点或副本差异，再调整数据或请求的分配方式 |
| 依赖服务慢 | 跨服务调用记录（分布式 trace）、远程调用（RPC）各阶段耗时、超时/重试次数 | 向被调用服务传递请求截止时间（deadline）、控制重试、必要时降级 |

不要把“QPS 不变”误读成“工作量不变”：查询类型和频率分布、倒排列表长度、命中率、段数、每请求评分量都可能变化。也不要从“发布后发生”直接推断因果，需要比较新旧版本，并对照 CPU、磁盘等资源指标的变化时间。

### 一次合格的实验应该怎样描述

1. 选定一个假设，例如“新版本段数增加，导致解码量上升”。
2. 在请求数量与类型相近的情况下观察单请求段访问数、解码的倒排记录数和执行耗时的关联。
3. 用固定查询集与相同资源对照新旧版本，记录并控制缓存是否已预热、同时运行多少请求等条件。
4. 若通过回退/减少段数改变一个因素后相应指标恢复，再评估全量修复；同时检查错误率、拒绝率是否上升，以及是否漏掉原本应返回的文档。

必要时可以先恢复旧版本、限制合并、减少接收的流量或扩容，但应根据已掌握的原因选择，并说明对业务的影响。禁止“只要 P99 下降就是修好了”，因为大量拒绝或提前超时也会让已完成请求的延迟看起来变好。

## 分位数和容量的常见误区

- 不同阶段的 P99 通常不是同一批请求，不能直接相加；应使用请求的调用记录查看同一条慢请求在各阶段的实际耗时。
- 有界队列把部分等待变成拒绝，所以必须同时看错误、超时和拒绝。
- 当到达和处理速率长期稳定时，Little's Law（利特尔定律）给出 L=λW：系统内平均请求数等于平均吞吐率乘以平均停留时间。这不是 P99 公式，也不能直接套到请求持续积压的过程。
- 压测若每次等上一请求返回才发下一个，会随服务变慢自动降低请求发送速率，可能低估过载时的尾延迟；需要说明压测是按固定速率发送请求，还是等待上一个响应后再发送。

## 复杂度与简化范围

队列单次操作通常 O(1)，容量 C 的空间 O(C)；示例还存 R 条测量记录，O(R)。实际服务应将耗时按区间统计到直方图等有空间上限的结构中，只抽样保留部分请求记录。避免给每个用户 ID 或请求 ID 建立独立指标序列，否则标签取值过多，会使监控系统的存储和处理成本急剧增加。

示例未采集系统级 CPU、锁或 I/O 数据，也未计算小样本分位数。源码输出只证明计时框架可运行，不能推导线上性能结论。

## 分层追问与参考答案

- **基础：为什么用 steady_clock？** 计算时间间隔需要不会倒退的单调时钟，避免系统日期和时间被校准后影响测量。
- **资深：线程池加倍可能更慢吗？** CPU 或内存带宽已经接近处理上限时更多线程带来调度与缓存成本；I/O 等待场景才可能从更多并发获益，仍不能超过被调用服务允许的并发数。
- **资深：锁等待与 I/O 等待如何区分？** 结合线程栈、等待事件和资源指标，而不是仅看 CPU 利用率。
- **专家：如何确保优化没损害召回？** 使用固定查询集，对照优化前后的文档集合和排序，并记录哪些请求减少了处理步骤或提前超时；只有业务明确允许近似结果时，才接受相应的结果差异。

## 评分与验证

基础达标为排队/执行分解；资深达标为为每个可能原因提出能够支持或排除它的测量方法；专家加分是压测请求如何发送、分位数的正确使用，以及如何检查是否漏掉匹配文档。面试官逐步提供证据后允许调整判断，记录调整依据；一直列工具名或直接认定根因不算深度。隐瞒拒绝来宣称延迟改善是严重评价错误。

运行 `make run eng_latency_diagnosis`：确定性验证接收 2、拒绝 1、处理完队列任务且保持先进先出顺序，以及单调计时的非负性。测试不要求某个微秒数或吞吐阈值。
