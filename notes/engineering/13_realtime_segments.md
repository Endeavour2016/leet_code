# 13｜实时索引：明确更新何时可查、如何选择版本、怎样合并

> 复习主线：更新先保存在暂存区，刷新后才参与查询；先选择文档的最新版本，再判断是否匹配；合并索引段不应改变查询结果。

## 面试题目（提供给候选人）

设计支持文档更新、删除、近实时查询的索引。先写一个内存模型，演示暂存区（pending）、构建后不再修改的索引段（segment）、刷新（refresh）和合并（merge）；再解释如何加日志恢复，以及合并时如何避免已更新或删除的旧文档再次出现在查询结果中。

- 建议 35～40 分钟，以设计讨论为主；现场只写版本归并或查询核心。
- 输入 `(外部 ID, version, deleted, terms)`；同一个 ID 的新版本号必须大于此前版本号。
- write 只把更新保存在暂存区；refresh 将暂存数据变为新的索引段，查询才能读到；查询按外部 ID 排序。
- 单线程模型，merge 覆盖当前所有已发布段，保留删除标记（tombstone，记录某个 ID 已在某个版本被删除）；不实现磁盘存储、并发合并或按词建立倒排列表。

## 面试官答案：先用一张状态图分开三种动作

```text
write → pending（只让写入者看到）
             ↓ refresh
       segments（查询可见，旧段不修改）
             ↓ merge
       更少的 segments（逻辑结果相同）
```

查询不读取 pending。merge 只处理查询已经可读的索引段，不能将尚未 refresh 的更新提前加入查询结果。示例明确区分了“接受更新”和“对搜索可见”。Elastic 对 [near real-time search](https://www.elastic.co/docs/manage-data/data-store/near-real-time-search)的说明可作为 refresh 行为的实际参照。

### 先解决版本，再判断是否命中

假设 A 的 v1 包含 phone，v2 改成 book。查 phone 时，如果只收集各段中包含 phone 的记录，就会找到旧段中的 v1，却忽略新版本 v2 已经不包含 phone，最终错误地返回 A。

**必须始终保证的条件：每个外部 ID 只以已发布的最高版本参与查询；最新版本不含该词或已删除时，不能因为旧版本匹配就返回旧版本。**

📌 代码依据：[RealtimeIndex::search](../../engineering/retrieval/13_realtime_segments.cpp)：

```cpp
Segment visible = resolve();
std::vector<std::string> result;
for (const auto& pair : visible) {
  if (!pair.second.deleted && pair.second.terms.count(term)) {
    result.push_back(pair.first);
  }
}
```

源码为了清楚展示版本选择规则，每次扫描段并按 ID 选最高版本。生产实现可以使用版本映射、记录文档是否有效的位图（live-doc bitmap）和倒排游标减少扫描，但必须保证同一个外部 ID 只按最高已发布版本参与查询。

### 合并为什么不能随意丢弃删除标记

删除也是有版本的记录。若只保留“有内容”的记录，旧段、落后副本或重放日志可能把被删对象带回来。本例 merge 保留删除记录，同时保存接收过的最高版本，拒绝旧版本再次写入。

要清理删除标记，必须确认旧段、恢复时重新执行的日志、以及其他副本同步过来的数据，都不会让旧文档再次生效；局部合并尤其不能只看参与合并的几个段。

## 从内存模型扩展到线上设计

| 关注点 | 可讨论的方案与边界 |
|---|---|
| 持久性：重启后数据还在不在 | 先记录预写日志（WAL），再按约定返回写入成功；如果承诺断电后不丢失，就必须考虑何时将日志可靠地写入存储设备，例如完成 fsync |
| 可见性：查询何时能看到更新 | refresh 后查询可以使用新数据，但这不自动表示数据已可靠保存到磁盘 |
| 恢复 | 读取上次保存的有效索引段文件列表，再执行尚未包含在这些段中的日志；按版本判断操作是否已执行，避免重复恢复改变结果 |
| 原子提交：要么使用旧文件列表，要么使用完整的新列表 | 先完整写入并校验新段，再原子替换索引段文件列表；崩溃恢复时不能读到只写了一半的新列表 |
| 并发合并 | 先确定本次要合并的段，后台生成新段，再同步更新有效段列表；合并期间新增的其他段也必须保留 |
| 资源控制 | 限制合并并发和 I/O，观察段数、删除占比、refresh 延迟与少量慢查询的耗时 |

[Elastic translog 文档](https://www.elastic.co/docs/reference/elasticsearch/index-settings/translog)用于对照日志与持久化职责；上表是本题的设计讨论，不声称完整复现某个引擎。

## 复杂度与示例边界

设已发布记录总数 R、唯一外部 ID 数 D，示例 resolve 约 O(R log D)，还包含记录与 terms 的复制成本，临时空间 O(D＋对应 terms)。每次查询都扫描全部记录，因此不适合每秒查询量（QPS）很高的服务；它只用于验证版本选择规则。refresh 和 merge 都复制/移动内存段，不提供崩溃恢复或资源耗尽后的恢复。

## 分层追问与参考答案

- **基础：write 成功后为何查不到？** 尚未 refresh；必须在接口里说明接受、可见、持久化分别何时完成。
- **资深：相同版本重试怎样处理？** 本例拒绝 `version <= latest`；服务可把完全相同版本与内容视为成功，且不重复修改数据，这称为幂等处理，但同版本不同内容必须处理冲突。
- **资深：删除后新版本重建合法吗？** 合法，前提是版本更大；这与重放旧版本导致的复活不同。
- **专家：合并为什么影响 P99（99% 的请求耗时不超过的值）？** 争用磁盘、内存带宽、CPU 和缓存；同时旧查询持有旧段使峰值空间上升，应对照合并发生时间、资源占用、新段启用和旧段释放时间进行排查。

## 评分与验证

基础达标需说明暂存数据与可查询索引段的区别，以及 refresh 何时生效；资深达标为“先版本后匹配”及删除；专家加分为 WAL、清单提交与并发发布。提示“A 从 phone 改成 book”后识别旧版本命中，记提示后修复；认为 merge 可以任意丢删除标记为严重错误。

运行 `make run eng_realtime_segments`：刷新前后、替换词、拒绝旧/同版本、删除、合并后被删文档不再出现、新版本重建、多 ID 合并前后结果一致，merge 不提前发布 pending。
