# 12｜Top K 安全剪枝：只有确定不会影响前 K 名，才跳过评分

> 复习主线：比较当前第 K 名的分数与一块文档可能得到的最高分；整块文档都不可能入选时，才跳过它们。

## 面试题目（提供给候选人）

Top K 指排序最靠前的 K 个文档。给定每个文档在两个查询词上的非负整数分数，用两项之和排序。将文档分组，每组称为一个块；如果能证明块内文档都不可能进入前 K 名，就跳过这一块的评分，这叫剪枝。结果必须与全量评分一致，支持资格过滤和同分按 docID 升序。

- 建议 30 分钟；考察怎样在不漏掉正确结果的前提下减少评分、怎样维护前 K 名，以及同分时如何决定先后。
- docID 全局唯一；两项分数均为 uint32_t，用 uint64_t 求和避免溢出。
- 各块的辅助统计信息预先构建；不匹配某个查询词时，其分数可以为 0。先排除不符合条件的文档（如不允许投放的广告），再让文档参与 Top K。
- 本例直接接收已经算好的两项分数，只展示如何根据分数上界跳过文档；WAND 和 Block-Max WAND（BMW）是实际检索中的 Top K 优化算法，涉及遍历多个倒排列表，本题在追问中讨论，不实现完整算法。

`build_blocks(docs, block_size, output)` 成功返回 true。block_size 为 0 时返回 false，output 保持不变；合法的空输入成功生成空块列表。

## 面试官答案：先用完整计算得到标准答案，再尝试减少评分

作为对照的简单实现先对全部符合条件的文档算分，按“分数降序、docID 升序”排序，截取前 K。优化版本维护大小 K 的堆，堆顶是保留结果中最差的一项。

当堆还没满，任何低分文档都有机会进入结果，不能使用第 K 名门槛剪枝。堆满后，门槛只会变好，不会变差。

### 上界为什么安全

对某个块 B，分别记录两项分数的最大值 `max_a(B)` 和 `max_b(B)`：

```text
任意 d∈B：a(d) ≤ max_a(B)，b(d) ≤ max_b(B)
因此 score(d)=a(d)+b(d) ≤ max_a(B)+max_b(B)=UB(B)
```

这两个最大值即使来自不同文档，它们的和也不会小于块内任何文档的实际总分，因此可以作为分数上界。这个上界可以比实际最大分数大：这样只会少跳过一些块；但不能比实际最大分数小，否则可能错误跳过应当入选的文档。

**必须始终保证的条件：堆保留已评分合格文档中最好的 K 个；跳过块里的任何文档都不能超过当前门槛。**

📌 代码依据：[topk](../../engineering/retrieval/12_topk_pruning.cpp)：

```cpp
if (best.size() == k && block.upper_bound < best.top().score) {
  continue;
}
for (const auto& d : block.docs) {
  if (d.eligible) {
    ++scored;
  }
```

### 为什么上界等于当前第 K 名分数时，不能直接跳过

当前堆顶 `(score=10, docID=9)`，下个块上界也是 10，但里面可能有 `(10,1)`。按照题目规定的同分排序规则，docID 1 应排在前面，因此不能用 `UB <= threshold` 跳过。示例只用严格小于；若想等于时也跳，必须把 docID 等排序条件一起考虑，证明该块没有文档能够排进前 K 名。

过滤同样不能后置到取完 K 之后，否则堆里可能塞满不合格文档，导致少结果甚至错误阈值。块上界包含被过滤文档的贡献仍然安全，只是可能比合格文档的实际最大分数大，从而减少可以跳过的块数。

## 复杂度与真实检索的联系

预建块 O(N)，教学代码存文档和元数据 O(N)；查询 O(B＋V＋M log K＋K log K)，B 为访问块数，V 为未剪枝块中遍历的文档数（包括被过滤的文档），M 为实际评分的合格文档数，结果堆 O(K)。最坏情况没有块可剪，算法仍要评分所有文档。

源码把块构建放在查询前；若为了求上界，查询时再次给块中每个文档完整评分，就没有展示减少评分工作的收益。实际系统的上界通常要与查询权重、评分函数和索引统计配合，不能把本例预计算的两项贡献直接当作通用查询索引。

Lucene 的 [Scorer 接口](https://lucene.apache.org/core/9_12_1/core/org/apache/lucene/search/Scorer.html)提供 `advanceShallow`、`getMaxScore`、`setMinCompetitiveScore` 等接口，可用来对照三种用途：先移动到目标附近的块而不逐个评分、读取分数上界、告知评分器当前进入 Top K 所需的最低分。本例没有实现这些 Lucene 接口。

## 分层追问与参考答案

- **基础：为什么不是大顶堆？** 要快速淘汰当前最差结果，堆顶必须是最差的一项。
- **资深：WAND 与本例有什么区别？** WAND 将多个倒排列表的当前 docID 排序，逐项累加各词的分数上界；累计值达到当前 Top K 所需最低分时，对应位置称为 pivot（候选分界位置）。算法据此跳过不可能达到所需分数的文档。本例直接检查整个文档块，没有实现这种多列表遍历。
- **资深：BMW 增加了什么？** 使用某个词在当前数据块中的分数上界，通常比该词在整张倒排表中的上界更接近实际分数；还需要处理不同 posting 的块边界和游标推进，不能只加一个数组就宣称完整 BMW。
- **专家：加业务加权（boost，例如提高某类文档的分数）、负权重或浮点打分后呢？** 重新推导完整评分的上界。负权重会改变该取最大还是最小的贡献；浮点舍入可能低估，必须确保计算出的上界不会低于实际可能得到的分数，不能照搬本例公式。

## 评分与验证

基础达标为 Top K 堆；资深达标需独立证明上界并识别同分反例；专家加分为过滤、权重与浮点边界。提示“同分有第二排序键”才改严格比较记提示后完成；没有先与完整计算结果对照就只比较耗时，或使用低估上界，属于严重缺陷。

运行 `make run eng_topk_pruning`：与穷举对照，覆盖 K=0、K 大于命中数、空数据、随机顺序、同分、过滤和最大整数贡献，并验证示例确实少评分了文档。
