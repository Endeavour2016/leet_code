# 08｜Bloom Filter：用较少内存排除不存在的元素

> 复习主线：查询 key 对应的多个位：只要有一个为 0，key 就不在集合中；全部为 1 时仍需精确查找。

## 面试题目（提供给候选人）

Bloom Filter（布隆过滤器）用于快速判断元素是否可能存在。给定预计元素数 n 和目标误判率 p，实现只增不删的 Bloom Filter，支持 uint64_t key 的 add 与 may_contain。解释如何用于检索索引，以及为什么不能直接替代精确判断。

- 建议 25 分钟；考察允许少量误判的数据结构、内存与误判率的取舍，以及如何解释查询结果。
- n>0，0<p<1；由单线程完成插入，再交给查询线程只读使用；不实现并发插入。
- 构造后先检查 `valid()`；参数无效或超过教学规模上限时为 false。
- `may_contain(key, result)` 的返回值表示查询是否成功。成功时 result 为 false 表示一定不存在，为 true 表示可能存在；失败时 result 保持不变，不能据此过滤文档。`add` 同样用 bool 报告是否成功。

## 面试官参考答案：从反例理解误判

普通 Bitmap 用整数编号直接定位一个位，Bloom 用哈希函数把任意 key 映射到一张有限的位图。不同 key 可以共享位置，因此它是概率过滤器，不能替代精确集合。

先假设位图长度 m=10，每个 key 取 k=3 个位置，不急着看参数估算：插入时将这 3 位全部设为 1；查询时检查相同的 3 位，只要其中一位为 0 就返回“不存在”。所有 key 共用一张位图，并不是每个 key 分配一张。

插入 A，把位置 2、5、8 置为 1；插入 B，把位置 1、5、9 置为 1。查询 C 恰好访问 2、5、9，虽然没插入过 C，也会得到“可能存在”。

但已插入 A 的 2、5、8 不会自己变回 0，所以在只插入、不清除位的前提下不会把 A 判为不存在。这个保证来自数据结构操作，与哈希分布好坏无关；分布影响的是误判率。若查询 D 的位置为 0、5、9，其中第 0 位尚未设置，就可以确定 D 没有插入过。

**必须始终保证的条件：只会置位，不会清位；插入与查询对同一个 key 必须使用完全一致的位置序列。**

📌 代码依据：[BloomFilter::visit](../../engineering/index/08_bloom_filter.cpp)：

```cpp
const auto h1 = mix(key);
const auto h2 = mix(key ^ UINT64_C(0x9e3779b97f4a7c15)) | 1;
for (std::size_t i = 0; i < hashes_; ++i) {
  if (!f((h1 + i * h2) % size_)) {
    return false;
  }
}
return true;
```

add 和 may_contain 共用位置生成逻辑，前者把对应位设为 1，后者检查这些位是否全为 1。示例先计算两个哈希值 h1、h2，再用 h1+i×h2 生成多个位置，称为双哈希。其理论背景见 [Kirsch 与 Mitzenmacher 论文](https://www.eecs.harvard.edu/~michaelm/postscripts/esa2006a.pdf)。示例是固定整数混合函数，非加密哈希；无符号运算按机器整数宽度取模，经验误判率需要实测。

## 参数只需记住推导方向

若有 m 位，一个近似均匀的哈希把某一位避开的概率为 `1 - 1/m`。插入 n 个元素、每个取 k 个位置后，该位仍为 0 的概率近似为 `(1 - 1/m)^(kn) ≈ exp(-kn/m)`。未插入 key 的 k 个位置碰巧全为 1，就形成误判；按独立性近似得到下面的误判率。实际双哈希的位置并非完全独立，因此这是估算。

在理想均匀哈希近似下：

```text
m ≈ -n ln(p) / (ln 2)^2          位数
k ≈ (m/n) ln 2                  哈希次数
p_actual ≈ (1 - exp(-kn/m))^k    当前负载的误判率估算
```

n 越大，需要更多位；p 越小，需要更多空间和探测。比如 n=10000、p=1%，约 95851 位，即约 12 KB，k 约 7。整数取整、位置相关性和实际数据会使测量偏离估算。

复杂度：查询和插入 O(k)，空间 O(m) 位。源码显式限制最多 1 亿位，仅为教学例子控制分配规模，不是 Bloom Filter 算法本身的限制。

## 怎样用于检索

```text
查询词或 key → Bloom 判断不存在 → 跳过对应索引段或磁盘查找
                    ↓ 可能
                继续查词典或倒排列表，确认是否存在
```

适合大量不存在查询、而精确访问较贵的场景。若精确查找所需的数据已经在缓存中，Bloom 的哈希与访存成本可能不划算。广告资格等精确过滤不能仅凭查询结果“可能存在”放行。

## 分层追问与参考答案

- **基础：为什么不能删除时把 k 个位清零？** 这些位可能也属于其他 key，清零可能把仍然存在的元素误判为不存在，称为假阴性。Counting Bloom Filter 使用计数器代替单个位，但还需处理计数器溢出，并保证不会删除从未插入的元素。
- **资深：实际元素数超过 n 会怎样？** 位越来越满，误判率升高；通常需要扩容重建或分层结构，而不是简单延长原位数组继续使用旧映射。
- **进阶：哈希次数越多一定越好吗？** 不是。固定 m、n 时，次数太少区分能力不足，太多又会很快把位图填满；近似最优值是 `(m/n) ln 2`，实现取整并至少使用一次。
- **进阶：能统计插入过多少个不同 key 吗？** 不能直接数 1：一个 key 会设置多个位，不同 key 又可能共用位。布隆过滤器不保存精确成员数，也不能枚举原始 key。

## 评分与验证

基础达标需写对多位置置位和查询，并解释“可以把不存在误判为存在，但不能把已插入元素判为不存在”；进一步看能否解释参数估算、元素过多导致误判率上升，以及为何不能直接删除。提示“两个 key 共用一个位”后发现删除问题记提示后完成；把“可能存在”当精确存在，或把查询失败当作“不存在”，都是严重错误。不要求并发与持久化设计。

运行 `make run eng_bloom_filter`：检查已插入 10000 个 key 全部可查，固定种子测试 10 万个未插入 key 并打印误判率，不要求每次测量都恰好等于理论误判率。
