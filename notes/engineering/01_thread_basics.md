# 01｜C++11 多线程：先想清楚谁拥有数据

> 复习主线：生命周期 → 共享状态 → 等待条件 → 结果与状态。先说明哪个线程写数据、哪个线程读数据，再选择需要的标准库接口。

## 面试题目（提供给候选人）

用 C++11 写一个线程生成数据、另一个线程等待并读取数据的示例。前者称为生产者，后者称为消费者。再演示并发计数，以及把子线程的结果和执行状态交回主线程。解释如何保证线程退出、如何避免线程继续访问已经销毁的对象（悬空引用）。

- 建议 20 分钟；考察线程如何启动和退出、如何防止多个线程不安全地访问同一变量，以及如何让读线程看到写入结果。
- 输入：生产者生成整数 42；两个线程分别计数 10000 次；一个任务返回失败状态。
- 输出：消费者读到 42、最终计数 20000、主线程读到任务失败状态。
- 不要求实现通用并发框架，不使用 `detach()` 将线程分离后任其继续运行，因为这不能解决被引用对象何时销毁的问题。

## 面试官答案：从四个问题推导

**第一问：线程结束前，它引用的对象还在吗？** lambda 的 `[&]` 通过引用访问外部对象，不会延长对象的生命周期。应在这些对象销毁前调用 `join()`，等待使用它们的线程结束。示例把 join 写进包装对象的析构函数，无论执行到函数末尾还是提前 return，都能等待线程结束。这种利用对象生命周期管理资源的做法称为 RAII。

**第二问：共享数据是否真的需要 atomic？** `std::atomic` 提供原子操作，避免一个操作在多个线程间被拆开执行。但如果数据 `payload` 和就绪标志 `ready` 的所有读写都先获得同一把互斥锁 `std::mutex`，就可以使用普通变量：线程检查 ready 并读取 payload 期间，其他线程不能修改它们。

**第三问：消费者等待的是通知还是条件？** 通知只是提醒“可以重新检查了”，`ready == true` 才表示数据已经准备好。`wait(lock, predicate)` 中的 predicate 是返回 bool 的判断函数，也叫谓词。wait 等待时释放互斥锁，返回前重新获得锁；即使没有收到通知却意外被唤醒（虚假唤醒），也会重新检查条件，不满足就继续等待。

**第四问：子线程怎样报告任务失败？** 定义包含 `ok` 和 `value` 的结果结构体，子线程通过 `promise.set_value()` 写入，主线程通过 `future.get()` 等待并读取。`ok == false` 表示业务失败，此时不使用 value。promise 负责写入，future 负责读取，二者关联同一份结果存储。每个 promise 只设置一次结果，每个普通 future 只调用一次 get；本例不用异常传递错误。

### 核心框架

📌 代码依据：[消费者等待与生产者发布](../../engineering/concurrency/01_thread_basics.cpp)，下面是消费者核心片段：

```cpp
std::unique_lock<std::mutex> lock(mutex);
cv.wait(lock, [&] {
  return ready;
});
observed = payload;
```

生产者也持同一把锁，先写 payload，再把 ready 设为 true，释放锁后调用 `notify_one()` 通知消费者。即使 notify 发生在消费者开始等待之前，消费者检查 ready 也能直接继续，因此没有“丢一次通知就永远卡住”的问题。

```text
生产者：lock → payload=42 → ready=true → unlock → notify
消费者：lock → 检查 ready → 不满足则释放锁等待 → 重新获得锁 → 读 payload
主线程：join 消费者 → 读取 observed
```

### 几个 API 各自负责什么

| API | 解决的问题 | 复习时抓住的点 |
|---|---|---|
| `thread` + join | 启动线程、等待线程结束 | 尚未 join 或 detach 的 thread 对象不能直接销毁，否则程序会终止 |
| `lock_guard` | 保护共享数据的访问 | 对象创建时获得互斥锁，离开作用域时释放锁 |
| `unique_lock` | 可释放、重新获得锁 | 条件变量需要它 |
| `condition_variable` | 等待状态变化 | 持有同一把锁时检查等待条件、修改共享数据 |
| `atomic` | 单个原子对象的访问 | 保证计数不丢失，不自动保证其他变量可以安全读取 |
| `promise/future` | 一次结果交接（可包含失败状态） | future 通常只能 get 一次 |
| `async` | 创建带结果的任务 | async 异步执行；deferred 延迟到 wait/get 时执行 |

## 正确性、复杂度与边界

计数使用 `memory_order_relaxed`：它保证计数的增加是原子操作，不额外约束其他变量的读写顺序。本例只需要计数不丢失，而且主线程在两个工作线程都 join 之后才读取结果；没有通过计数值来判断其他数据是否可读，因此这种内存序已经足够。执行 N 次计数为 O(N)，示例额外空间 O(1)，无法保证线程调度和等待互斥锁所需的最长时间。

负责 join 的包装对象应由外部线程管理，不能在它所管理的线程中销毁，否则会尝试等待自己结束。主线程不能持有工作线程退出所需的锁再 join。完整示例还验证 `launch::deferred` 在 get 时才执行；默认 async 策略允许延迟执行，不应当成“必定新开线程”。

## 分层追问与参考答案

- **基础：为什么不能用 volatile 修复计数竞争？** 它不能代替互斥锁或原子操作。`++` 包含读取、加一、写回，多线程同时操作仍可能丢失更新。
- **资深：把 ready 改成 atomic，payload 就安全吗？** 需要配合内存序：生产者先写 payload，再用 release 操作把 ready 设为 true；消费者用 acquire 操作读到这次写入的 true 后，才能安全读取 payload。release/acquire 配对建立了两个线程之间必要的执行顺序；只使用 relaxed 不够。
- **资深：为什么丢弃 async 返回的 future 可能看起来串行？** 对于以 `launch::async` 启动的任务，如果返回的 future 临时对象被立即销毁，销毁过程可能要等待任务完成。反复这样调用会让任务看起来逐个执行；可以先保存各个 future，再逐个 get 获取结果。
- **专家：为什么线程数越多不一定越快？** 锁争用、调度、缓存失效和内存带宽可能成为瓶颈；先确认任务主要在做计算还是等待 I/O，以及系统允许同时处理多少任务。

## 评分与验证

- **基础达标**：能独立写出 join、带条件检查的 wait 和状态传递，指出引用生命周期。
- **资深达标**：能画出同步关系，解释 relaxed 在本例为何足够；专家加分看是否主动讨论持有互斥锁时调用 join 的风险，以及 async 的启动策略。
- 提示“通知不是状态”后能修正 if/wait，只计提示后完成；仍然在没有同步措施的情况下反复读取另一个线程修改的普通 bool 变量属于严重正确性错误。
- 验证：从实现上检查通知先于等待、等待先于通知这两种执行顺序都应正确，计数准确、失败状态可读取、deferred 延迟执行。入口：`make run eng_thread_basics`。
