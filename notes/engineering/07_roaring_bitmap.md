# 07｜Roaring Bitmap：按编号区间选择数组或位图

> 复习主线：32 位 ID 分成高 16 位和低 16 位；高位决定放在哪一组，低位用数组或位图保存，具体取决于这一组里有多少元素。

## 面试题目（提供给候选人）

实现一个教学版 Roaring Bitmap，支持 uint32_t 插入、查询和交集。每组数据使用 array（有序数组）或 bitmap（位图）容器保存，元素少时使用数组，元素多时自动转为位图，并解释选择阈值。

- 建议 30 分钟讲设计，现场只写按高位分组和一种交集实现；完整代码供课后复习。
- 不要求保存连续区间的 run container、删除、序列化（转换为可保存的字节数据），或 SIMD 优化（用一条处理器指令同时处理多个值）。
- 同一 ID 多次插入不增加成员；覆盖完整 uint32_t 值域。

## 面试官参考答案：为什么只在局部作选择

普通 Bitmap 的空间取决于整个编号范围，有序数组的空间取决于实际元素个数。检索过滤集合经常“有些 ID 区间很密，有些很稀”，没有必要让所有区间共用一种表示。

```text
uint32 docID = [高 16 位 | 低 16 位]
                     ↓
map<高位, Container>：
  0000 → array  [1, 8, 100]
  0001 → bitmap [65536 个 bit]
  FFFF → array  [65535]
```

这里将高 16 位相同的 ID 分为一组，通常称为一个桶；每组包含 65536 个可能的低 16 位值。数组用 uint16_t，每个元素占 2 字节；位图固定 `65536/8=8192` 字节，所以 4096 个元素时，两种方式存储元素本身所占的空间相等。这是忽略记录类型、长度等辅助信息和内存分配的开销的理论分界，不是所有机器的性能最优点。[官方格式规范](https://github.com/RoaringBitmap/RoaringFormatSpec/)也规定非 run 容器按这个元素数量阈值解释类型。

### 实现只抓三件事

例如 `65537 = (1 << 16) + 1`：高位为 1，低位为 1，所以它属于第 1 组，组内只保存 1。编号 1 则属于第 0 组，虽然低位相同，仍是不同成员。

1. 高位相同的 ID 放入同一容器。
2. array 始终有序且无重复，超过 4096 转为 bitmap。
3. 交集根据两侧容器类型选择计算方法。

📌 代码依据：[Container::add](../../engineering/index/07_roaring_bitmap.cpp)：

```cpp
auto it = std::lower_bound(array_.begin(), array_.end(), value);
if (it == array_.end() || *it != value) {
  array_.insert(it, value);
}
```

数组超过 4096 个元素时，建立 1024 个 uint64_t，将每个低位值 x 写到 `bits[x / 64]` 的 `x % 64` 位，再释放数组。每个值写入唯一位置，转换不会改变集合内容；重复插入也不会错误地增加成员数。

**必须始终保证的条件：数组与位图可以互相转换，但成员不能丢失或增加；交集只发生在相同高位桶之间。**

| 左 × 右 | 核心交集方法 | 时间复杂度（a、b 为数组中的元素数） |
|---|---|---|
| array × array | 双指针交集 | O(a+b) |
| array × bitmap | 枚举 array，查询 bitmap 中对应的位 | O(a) |
| bitmap × bitmap | 1024 个 uint64_t 按位 AND | O(1024)，另加结果计数 |

一个编号区间中元素占比高称为稠密，占比低称为稀疏。两个位图求交后，如果剩余元素不多，就转回 array。示例从位图转回数组时，直接扫描 65536 个可能的位置，不加入位扫描指令优化；复习只需理解为什么交集结果也应按元素数量选择数组或位图。

## 复杂度与实际 Roaring 库的差别

顶层 map 查桶 O(log B)，B 为桶数；稀疏插入需要移动数组元素，O(a)，不能仅因使用 lower_bound 就说整个插入 O(log a)。顶层交集遍历一侧桶并查询另一侧，再加各容器交集成本；教学版允许保留空结果桶。

空间随实际桶分布变化，约为各桶 `min(2×成员数, 8192)` 元素存储空间加类型、长度等辅助信息。这里没有完整 Roaring 文件布局，不能与 CRoaring 或其他库直接交换序列化结果。

## 分层追问与参考答案

- **基础：为什么不是全局达到 4096 个元素就转位图？** 阈值适用于每个低 16 位局部值域，全局元素数不反映局部密度。
- **资深：连续长区间还可以怎么压？** run container 保存起点和长度，成本取决于连续段数量；选择时比较表示成本，不只看成员数。
- **资深：何时会不如普通 Bitmap？** 值域较小且整体稠密、频繁整表位运算时，分桶查找与容器分支可能是额外负担。
- **专家：批量构建怎样更快？** 先排序去重，按高位顺序构建容器，减少逐次 vector 插入和反复查桶；测数据分布与实际查询运算，而非只测 contains。

## 评分与验证

基础达标为高低位拆分与阈值推导；资深达标为三种容器组合的交集计算方法；专家加分看是否能解释连续区间压缩、批量构建和数据分布对性能的影响。提示“局部密度”后修正全局阈值记提示后完成；把此实现称为完整兼容 Roaring，说明没有分清教学示例和完整库实现。
