# 02｜有界阻塞队列：明确队列关闭后的行为

> 复习主线：使用一把互斥锁保护队列；队列满时等待空位，队列空时等待任务；关闭后不再接收任务，但要取完已有任务。

## 面试题目（提供给候选人）

为检索任务实现容量为 C 的多生产者、多消费者队列。生产者是向队列添加任务的线程，消费者是从队列取出任务的线程。满时生产者等待，空时消费者等待；支持 close，关闭后拒绝新任务，但消费者仍能取完已接收任务。

- 建议 25 分钟；考察条件变量、队列关闭前后的行为，以及如何限制待处理任务数量。队列满时让生产者等待，是背压（backpressure）的一种做法，用来防止生产速度持续超过消费速度。
- `push(T)` 返回是否接收；`pop(T&)` 返回是否取到；`close()` 可重复调用。
- C 必须大于 0；关闭且已有任务全部取走后的 pop 返回 false；新增 `try_push` 供过载快速拒绝示例使用。

## 面试官答案：两个条件推导整个实现

生产者在队列满时等待空位，消费者在队列空时等待任务。调用 close 后，必须唤醒两类等待线程：生产者返回失败，消费者继续取出剩余任务，直到队列为空。

| 操作 | 结束等待的条件 | 醒来后怎么做 |
|---|---|---|
| push | closed 或 size < C | closed 则失败，否则入队 |
| pop | closed 或非空 | 空则结束，否则取一个 |
| close | 不等待 | 置 closed，唤醒两类线程 |

**必须始终保证的条件：读取或修改队列以及 closed 标志时，都必须持有同一把互斥锁（mutex）；关闭不清空队列。**

📌 代码依据：[BlockingQueue::pop](../../engineering/common/blocking_queue.h)：

```cpp
not_empty_.wait(lock, [this] {
  return closed_ || !items_.empty();
});
if (items_.empty()) {
  return false;
}
value = std::move(items_.front());
items_.pop_front();
```

wait 返回后，即使队列已关闭，只要里面还有任务，pop 就应取出任务。只有队列已经为空时才返回 false。如果改成 `if (closed_) return false`，关闭前已经接收的任务就可能无人处理。

push、pop 和 close 都在持有同一把互斥锁时修改状态，因此这些修改不会同时发生。如果 push 先把任务加入队列，随后 close 必须保留该任务；如果 close 先设置了关闭标志，随后 push 必须拒绝任务。

## 核心框架与复杂度

```text
push：等待空位或关闭 → 判断关闭 → 入队 → 通知消费者
pop ：等待任务或关闭 → 判断队空 → 出队 → 通知生产者
close：设置关闭 → notify_all 唤醒所有等待的生产者和消费者
```

底层 `std::deque` 的首尾插入和删除通常为 O(1)，空间 O(C)，等待时长没有上界。释放互斥锁后再通知，可以减少被唤醒的线程因为锁尚未释放而再次等待的情况。无论何时通知，线程都必须重新获得锁并检查等待条件。

元素类型遵守本项目不使用异常的约定。容量为 0 时 `valid()` 返回 false，队列处于关闭状态，push、try_push 和 pop 都立即返回 false；pop 失败时输出参数保持不变。队列析构前，调用者必须 close 并 join 所有访问线程；close 本身不负责 join。

## 分层追问与参考答案

- **基础：为什么用两个条件变量？** 一个通知等待空位的生产者，另一个通知等待任务的消费者。也可以共用一个条件变量，但必须重新检查等待条件和唤醒方式，避免只唤醒暂时无法继续的线程。
- **资深：为什么 close 用 notify_all？** 关闭是所有等待者都需要观察的终止事件，只唤醒一个可能让其他线程永远等待。
- **资深：满时阻塞一定适合在线检索吗？** 不一定。请求有截止时间（deadline），超过这个时间结果可能已经无用，长时间阻塞会占住调用线程；可快速拒绝、限时等待或降级，不能无限积压。
- **专家：有界队列能消除过载吗？** 只能限制积压；持续到达速率大于处理能力时仍需拒绝部分请求或减少接收的流量，并记录拒绝率和排队时间。

## 评分与验证

基础达标需写对两个等待条件；资深达标需解释 close 与 push 同时调用时如何决定是否接收任务；专家加分看是否能分析阻塞生产者会怎样影响上游服务。提示“关闭时队列中可能还有任务”后才发现丢任务，应记录为提示后修复；仍然不获取互斥锁就读取共享的 queue 或 closed，属于严重错误。

[测试入口](../../engineering/concurrency/02_blocking_queue.cpp)覆盖先进先出（FIFO）、满队列拒绝、关闭时唤醒两类线程、重复关闭，以及多生产者多消费者（MPMC）情况下任务不丢失、不重复。测试用 promise 通知主线程相关操作即将开始，但不能据此断言另一个线程已经进入等待状态；仍需检查先关闭和先等待两种顺序是否都被代码正确处理。运行 `make run eng_blocking_queue`。
