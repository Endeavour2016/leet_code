# 03｜极简线程池：让固定的一组线程反复执行任务

> 复习主线：提交者把任务放入队列；工作线程取出任务，释放互斥锁后执行；关闭时停止接收新任务，等待已有任务执行完。

## 面试题目（提供给候选人）

使用 C++11 实现一个固定有 N 个工作线程的线程池。调用者可以提交一个函数或 lambda，调用 `submit(task, future)` 时，返回的 bool 表示是否接受任务，输出参数 `std::future` 用于获取任务结果。任务用返回值表达业务成功或失败，不使用异常。线程池关闭后不再接受新任务，但必须完成已经接受的任务。

- 建议 30～35 分钟；考察共享队列的线程安全、任务结果的获取，以及线程如何正常退出。
- N > 0 时线程池有效；N = 0 时 `valid()` 返回 false，提交会被拒绝。提交的函数不接收参数，需要的数据通过 lambda 捕获。本题不要求实现复杂的参数转发。
- `shutdown()` 由管理线程池的外部线程调用，允许重复调用，但不允许多个线程同时调用，也不能由池内工作线程调用。其他线程可以同时调用 `submit()`。

## 面试官参考答案：先理解三个组成部分

| 组成部分 | 作用 |
|---|---|
| 任务队列 `tasks_` | 保存已提交、尚未被工作线程取走的任务 |
| 工作线程 `workers_` | 反复从队列取任务并执行，无需每来一个任务就创建线程 |
| 互斥锁 `mutex_` 和条件变量 `ready_` | 互斥锁防止多个线程同时修改队列；条件变量让没有任务的线程等待，避免一直循环检查 |

这里的“任务”就是调用者通过 `submit()` 提交的函数，例如处理一次检索请求。“工作线程”（worker thread）是线程池中负责执行这些函数的线程。

```text
调用者 → submit() → 任务队列 → 工作线程取出任务 → 执行任务
  ↑                                              ↓
  └──────── future.get() 获取任务结果 ──────────┘
```

## 与《多线程编程.md》中 C++11 线程池的对比

对比对象是工作笔记中 `c++11线程池demo` 一节的 `enqueue(F&& f, Args&&... args)` 实现，原始代码已保存到[工作笔记线程池参考副本](references/thread_pool_work_note.md)。

**阅读实现时，仓库版更简单；编写调用代码时，笔记版更紧凑。** 两份实现的并发原理相同，都是固定线程、共享队列、条件变量等待、释放互斥锁后执行，以及关闭时处理完已有任务。笔记版同样使用 `result_of`、`packaged_task`、`future` 和 `shared_ptr`，并没有省掉这层结果传递机制。

| 比较项 | 工作笔记版 | 仓库版 |
|---|---|---|
| 提交接口 | `enqueue(f, args...)`，直接返回 future | `submit(f, output)`，返回接单状态 |
| 参数处理 | 可变参数模板、`std::forward`、`std::bind` | 只接收无参数任务，需要的数据用 lambda 捕获 |
| 工作线程循环 | 嵌在构造函数的 lambda 中，嵌套较深 | 提取到 `work()`，可独立阅读 |
| 关闭方式 | 析构中关闭并 join | `shutdown()` 可显式调用，也由析构调用；允许顺序重复调用 |
| 拒绝任务 | 停止后抛出异常 | 返回 false，保留原有输出参数 |
| 0 个线程 | 仍可入队，但没有线程执行；池存活时 get 会一直等，销毁后未执行任务会产生 broken promise | `valid()` 为 false，提交被拒绝 |
| 示例代码 | 打印消息、暂停一秒、取平方结果 | `main()` 验证返回值、关闭、拒绝任务和并发提交等约定 |

例如提交一次加法，笔记版可以写 `auto result = pool.enqueue(add, 2, 3);`。仓库版把参数绑定明确写在调用处：

```cpp
std::future<int> result;
if (pool.submit([] { return 2 + 3; }, result)) {
  const int value = result.get();  // value 为 5
  // 在这里使用 value。
}
```

笔记版的 `Args...` 表示任意数量的参数类型，`std::forward` 保留转发参数的左值或右值属性，`std::bind` 把函数和参数保存成一个之后可以无参数调用的对象。这增加了接口适用范围，也增加了需要理解的语法和对象生命周期规则。仓库版用 lambda 表达同一意图，更适合先复习线程池。按值捕获会保存副本；按引用捕获则要求被引用对象一直存活到任务执行结束。

不能直接根据整个文件的长度比较实现复杂度：仓库版 `main()` 中有较多验证代码。建议先读 `work()` 和 `shutdown()`，再读 `submit()` 的结果传递，最后看测试。若练习只要求执行任务、不要求按任务获取结果，才可以进一步省去 future 这一层；当前题目要求返回结果，应保留它。

仓库版也有可读性取舍：`wait` 的条件满足后，队列为空就能推出线程池已经停止，因此 `if (tasks_.empty())` 足够；笔记版写 `if (stop && tasks.empty())` 更直观。两者在这里等价，少一个判断并不一定更容易读。

## 核心思路：取任务时加锁，执行任务前释放锁

### 1. 为什么取任务时必须加锁？

多个工作线程共用一个队列。如果两个线程同时查看队首、取出并删除任务，就可能重复取到同一个任务，或者破坏队列的数据结构。

因此，“检查队列、取出任务、从队列删除任务”必须在持有同一把互斥锁时完成。提交者向队列添加任务，也必须先获得这把锁。

**必须保证：每个成功提交的任务，只被一个工作线程从队列取走并执行一次。** 这是当前线程池正常运行、正常关闭时的保证，不涉及进程崩溃后的恢复。

### 2. 为什么执行任务前要释放锁？

任务从队列取出后，已保存到当前工作线程的局部变量 `task` 中。调用 `task()` 不需要继续访问任务队列，所以不应继续持有保护队列的互斥锁。

假设线程 A 取出一个耗时 100 ms 的任务。如果它执行任务时一直持有这把锁，线程 B 就无法取出下一个任务，提交者也无法向队列添加任务。这样，多个工作线程的任务执行会被迫串行进行。

**正确做法：持有互斥锁时取出任务，然后释放互斥锁，再调用任务函数。** 这样，线程 A 执行任务的同时，线程 B 可以取出并执行其他任务。

如果两个任务本身还要访问同一个业务对象，例如共同修改统计表，这个业务对象仍需要自己的同步措施。保护任务队列的锁不负责保证任意业务代码的线程安全。

### 3. 对照工作线程的循环

下面对应 [ThreadPool::work](../../engineering/concurrency/03_thread_pool.cpp) 的实现，增加了注释以说明互斥锁何时获得、何时释放：

```cpp
for (;;) {
  std::function<void()> task;
  {
    std::unique_lock<std::mutex> lock(mutex_);  // 获得保护队列的互斥锁
    ready_.wait(lock, [this] {
      return stopped_ || !tasks_.empty();
    });
    // wait 等待时会释放锁，返回前会重新获得锁。
    if (tasks_.empty()) {
      return;
    }
    task = std::move(tasks_.front());
    tasks_.pop();
  }  // 离开作用域，lock 析构，释放互斥锁
  task();  // 此时不再持有保护队列的锁，执行调用者提交的函数
}
```

互斥锁保护的那一段代码，通常称为**临界区（critical section）**。本例中，从队列取出任务的操作位于临界区，调用 `task()` 位于临界区之外。复习时直接记“先加锁取任务，再释放锁执行”，比记简称更清楚。

`wait` 的等待条件也很重要：线程池停止，或者队列里有任务，满足任意一个条件就不再等待。正常运行且队列为空时，工作线程继续等待，不会退出。

## 怎样区分提交失败和任务执行失败？

`submit(task, future)` 返回 false，表示线程池未接受任务，原有 future 保持不变。返回 true 只说明任务已入队，并不表示业务执行成功。

`std::packaged_task<R()>` 把返回类型为 R 的函数包装成任务，并将返回值保存给 future。任务可以返回 `TaskResult{ok, value}`：调用者先确认提交成功，再调用一次 `future.get()` 读取结果，根据 ok 判断业务是否成功。不要对提交失败后仍无效的 future 调用 get。

```text
工作线程执行 packaged_task → 保存任务返回值 → 调用者通过 future.get() 读取
```

C++11 的 `std::function` 要求保存的可调用对象可以复制，而 `packaged_task` 本身不可复制。示例用 `shared_ptr` 管理 packaged_task，再把持有这个 shared_ptr 的 lambda 放入队列。这样既能保留任务，也满足队列中 `std::function` 的要求。

`result_of`、`packaged_task`、`future`、`shared_ptr` 和移动语义的详细说明直接放在源码 `submit()` 附近；测试所用的 `promise`、`shared_future` 也在对应位置说明。

## 关闭线程池时怎样避免丢任务？

1. 获得互斥锁，把 `stopped_` 设为 true，然后释放锁。`submit()` 检查这个状态时也持有同一把锁，因此能明确决定一个任务是在关闭前被接受，还是在关闭后被拒绝。
2. 唤醒所有等待的工作线程。队列中还有任务就继续取出并执行；队列为空才退出。
3. 在不持有互斥锁的情况下，对每个工作线程调用 `join()`，等待它退出。不能拿着这把锁等待，否则工作线程可能因无法获得锁而无法完成退出。

`stopped_` 表示“停止接收新任务”，不表示“立即放弃已有任务”。读上面的循环可见：唤醒后检查的是队列是否为空，而不是看到 stopped 就直接返回。

本例编译时禁用异常。线程创建失败、标准容器分配内存失败等资源问题不在可恢复范围内；禁用异常不会使标准库自动返回错误码。若要求这类故障也能恢复，需要改用支持错误码的线程创建接口和明确的内存管理方案，不在这道极简题中展开。

## 复杂度与示例范围

提交和取出任务的队列操作为 O(1)，空间为 O(N + Q)，Q 是等待执行的任务数；关闭所需时间取决于剩余任务的耗时和线程调度。

极简版队列没有容量限制，不包含任务超时、取消、优先级或自动扩容。在线服务可结合第 02 题限制队列容量，避免请求持续积压；复习时先掌握工作线程循环和关闭流程。

## 分层追问与参考答案

- **基础：为什么不能持有保护队列的互斥锁执行 task()？** 其他线程无法取出或提交任务，任务执行会被迫串行。如果当前任务又调用 submit，还会尝试获得自己已经持有的非递归互斥锁，造成死锁。
- **资深：工作线程提交一个子任务，然后立即调用它的 future.get()，可能出现什么问题？** 如果所有工作线程都在等待子任务，队列中的子任务就没有可用线程执行。可避免在线程池内部同步等待子任务，或使用另一个线程池执行这些子任务。
- **资深：任务的提交顺序等于完成顺序吗？** 不等于。任务按队列顺序被取走，但执行时间与线程调度不同，完成顺序可能不同。
- **专家：如何增加任务取消？** 先区分尚未执行和正在执行的任务。前者可以从待执行集合中移除，并通过 future 通知调用者；后者通常需要任务定期检查取消标志并自行退出，不应强制杀死线程。

## 评分与验证

基础达标：能写出工作线程循环，关闭时完成所有已接受的任务。资深达标：能解释为什么执行任务前要释放互斥锁，如何区分提交失败与业务失败，以及提交与关闭同时发生时的处理。专家加分：能识别等待子任务导致的死锁，并说明无异常示例对资源耗尽的处理边界。

如果候选人在提示“执行任务时是否还持有互斥锁”后才修正，应记录为提示后完成。忽略提交失败后仍读取无效 future，或者关闭时丢弃已经接受的任务，是严重的正确性问题。

运行 `make run eng_thread_pool` 可验证任务返回值、执行次数、业务失败状态传递、重复关闭、拒绝新任务、析构前完成任务、单线程执行顺序，以及多个提交者与关闭操作同时运行的情况。复习实现时先读 class，验证细节放在 main 中。
