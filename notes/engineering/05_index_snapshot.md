# 05｜索引快照：发布新版本，不修改读者手里的旧版本

> 复习主线：构建完整新对象 → 原子更新指向当前索引的指针 → 查询线程保存所用版本 → 最后一个查询结束后释放旧对象。

## 面试题目（提供给候选人）

检索线程需要持续读索引，更新线程定期发布新索引。请设计一个 C++11 内存快照方案，使一次查询始终使用同一版本，且替换后旧索引不会被提前释放。

- 建议 20 分钟；考察查询线程何时能看到更新、旧索引何时释放，以及一次查询会不会混用不同版本。
- 一个更新线程、多个查询线程；快照是某一版本的完整索引数据，包含 version 和 documents，交给查询线程使用后不再修改。
- `acquire()` 返回指向只读快照的 shared_ptr，查询期间保留它即可防止该快照被销毁；不是持久化系统，也不要求增量复制。

## 面试官答案：把三个问题拆开

| 问题 | 解决机制 |
|---|---|
| 查询线程是否看到完整构建的对象？ | 更新线程构建完对象再用 release 操作写入指针；查询线程用 acquire 操作读取它，确保能看到此前的构建结果 |
| 查询过程中当前版本变了怎么办？ | 查询开始只调用一次 acquire()，整个查询都保存并使用返回的快照 |
| 旧对象什么时候释放？ | shared_ptr 引用计数到零 |

**这三个措施缺一不可：安全地替换当前索引指针；不修改已供查询使用的对象；查询结束前保留它的 shared_ptr，防止旧对象提前被销毁。**

📌 代码依据：[SnapshotStore::publish/acquire](../../engineering/concurrency/05_index_snapshot.cpp)，发布核心：

```cpp
auto next = std::make_shared<const Snapshot>(version, std::move(documents));
std::atomic_store_explicit(&current_, next, std::memory_order_release);
```

读取用 `std::atomic_load_explicit(&current_, std::memory_order_acquire)`，它同时取得安全的 shared_ptr 所有权，不能先读取裸指针，再尝试增加引用计数，因为这两步之间对象就可能已经被释放。

```text
查询 A ─持有─ v1 ──查询完成后释放
                 ↑ 当前索引指针原来指向它
更新线程构建 v2 → 修改当前索引指针
查询 B ─持有─ v2
```

例子直接构建 `const Snapshot`，不让其他代码保留能修改该对象的指针。仅仅向查询线程返回 `shared_ptr<const T>` 还不够：如果后台仍通过另一个非 const 指针修改同一对象，查询线程仍可能读到变化中的数据。

## C++11 边界、复杂度与代价

C++11 通过独立函数 `std::atomic_load` / `std::atomic_store` 原子地读写 shared_ptr，不能用 C++20 的 `atomic<shared_ptr<T>>` 写法。也不能一边原子读取 current，一边普通赋值 current。[WG21 shared_ptr 原子访问提案](https://open-std.org/jtc1/sc22/wg21/docs/papers/2008/n2632.html)可作机制背景。

获取快照不会复制整个索引，但增加和减少 shared_ptr 的引用计数需要线程同步，其原子读写也可能在内部使用锁，因此不能保证无锁（lock-free）。新版本构建成本取决于数据规模；峰值内存包括构建中的新版本和所有仍被读者持有的旧版本。多个慢查询可能同时保留多个历史版本，不能只预算两份。

本例由一个更新线程按版本顺序替换索引；若多个更新线程同时构建，较旧版本可能反而较晚构建完成，并覆盖较新版本，需要统一安排替换顺序或检查版本号。最后一个释放 shared_ptr 的查询线程可能负责销毁整个旧索引；如果销毁很慢，会使少量请求耗时明显增加，影响尾延迟（例如 P99，即 99% 的请求耗时不超过的值）。

## 分层追问与参考答案

- **基础：为什么不能 atomic 裸指针再 delete 旧对象？** 原子指针不保护读者已取得的旧对象，仍可能出现 use-after-free，即对象已经释放，查询线程却还在访问它。
- **资深：一次查询每个阶段都 acquire 一次可不可以？** 生命周期安全，但阶段间可能混用版本；应将同一个快照传给本次查询的各个处理步骤。
- **资深：快照发布成功就代表落盘了吗？** 不代表。本题只保证其他线程可以安全读取新对象；进程重启后要恢复数据，还需要日志、磁盘文件以及明确的写入完成规则。
- **专家：何时考虑 epoch/RCU？** 当测量发现很多查询线程同时修改引用计数，导致性能下降时。epoch 和 RCU（Read-Copy-Update，读-复制-更新）是延迟释放旧对象的方法：记录哪些线程还可能访问旧版本，等这些访问结束后再释放，以减少每次读取时的同步开销。它们需要额外处理读者登记、长时间查询和旧版本内存积压，不是直接去掉引用计数就安全了。

## 评分与验证

基础达标需说明如何安全替换当前索引指针，以及如何防止旧版本被提前释放；资深达标需分别解释新版本可见、对象不再修改和旧对象释放的条件；专家加分是峰值内存和析构延迟。提示“读者还拿着旧指针”后修复只计提示后完成；直接释放旧指针为严重错误。

运行 `make run eng_index_snapshot`：读者先持有 v1，发布 v2 后仍能读 v1，新 acquire 读 v2，旧查询线程结束后，weak_ptr 检测到旧快照已被销毁。用 promise 建立执行顺序，无固定 sleep。
